Rendered-markdown change highlighting — end-experience mockup

Scope: the rendered preview mode only (markdown.tsx / RenderedMarkdown) — not the raw line-diff view. Today, BlockView wraps an entire top-level markdown node (a whole <ul>/<ol>) in one highlight if any line inside it changed. This mockup shows moving that decision to per-<li> granularity, adding intraline (word-level) diff highlighting inside the changed item's text, and an always-visible hover/focus-triggered before/after detail — all placeholder content.

Complex item — fallback with no clean intraline diff

The detail marker is not shown on a normal edited item — the del/add spans already put old and new text on screen at once, so a reveal step would just repeat what's already visible. It only earns its place on the fallback path: when an item's markup is too complex for a clean word-level diff (e.g. edits inside a link or nested formatting), the item falls back to a whole-item highlight with no intraline breakdown — so old and new are NOT both visible, and the marker is the only way to see the actual before text.

Not addressed in this pass: the raw DiffView.tsx (line-based) view has a separate, unrelated bug — inserting/deleting an item in an ordered list shifts every subsequent item's number, and git's line diff marks the whole shifted tail as removed+added even though the content is identical, just renumbered. That's a different pipeline (parsePatch.ts / plain git diff text) and a different fix (ordinal-normalization before diffing) from the per-item rendered-view work shown above.
